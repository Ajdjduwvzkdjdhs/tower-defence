# position-tracker2（ハンドル回転の検知 / 3パターン比較）

俯瞰カメラで **「かき氷機のハンドルを回しているか」＝削り中か** を判定する Python ツール。
異なるロジックと使用ライブラリの組み合わせで **3 パターン（A/B/C）** と、実機で出た
誤判定への **対策版 3 パターン（D/E/F）** を実装してある。同じ入出力・同じ判定ゲートで
**中身だけ差し替えて見比べられる**ようにしてある。

`tools/position-tracker`（MediaPipe で**位置**を見て谷 channel を出す）とは別物で、こちらは
**回転（削り）**の系統。Unity への接続は未実施で、現状は共有テキストファイルに書くところまで。

## 旧ロジックと、そこで起きていた問題

> どちらかの手を中心として、もう片方の手の座標とのなす角を見て、一定フレーム以内での
> 角度変化が閾値以内なら削っていない／閾値以上なら削っている、と判定する。

このやり方は **「2 つの手が同時に、別々の場所に見えていること」が前提**なので、次の 2 つで壊れる。

| 問題 | 原因 |
|---|---|
| 手が一瞬カメラの範囲外に出ると判定が消える | 片方でも欠けると角度が定義できず、瞬間値で判定しているので即 OFF |
| ハンドルを回す時に手が重なると判定がうまくいかない | 2 点が同じ場所に来ると「なす角」が数値的に暴れる／左右の取り違えで角度が飛ぶ |

3 パターンとも、この 2 点を**設計で**外している。共通しているのは次の 3 つ。

1. **2 つの手の相対角を使わない**。回転中心は手の軌跡（またはROI）から決めるので、**手 1 つで成立する**。
2. **瞬間値で判定しない**。時刻付きの窓（回帰／FFT／フロー平均）で見るので、数フレームの欠落は結果を変えない。
3. **見失いは「計測不能（rpm=None）」として上げるだけ**。ON/OFF の粘り（ヒステリシス＋ホールド）は
   `common.ShavingGate` に一元化してあり、`holdSec`（既定 0.45 秒）未満の欠落は判定に出ない。

## 3 パターン

| | A: `rotate_landmark.py` | B: `rotate_flow.py` | C: `rotate_periodicity.py` |
|---|---|---|---|
| ライブラリ | mediapipe + opencv | **opencv のみ**（モデル無し） | ultralytics + opencv |
| 検出するもの | 手のひら中心（21 ランドマークの掌側 5 点の重心） | 何も検出しない（画素の動き） | 手首キーポイント（YOLO-pose） |
| 対象範囲 | **カメラ映像の全体**（調整不要） | 円 ROI（マウスで調整） | **カメラ映像の全体**（調整不要） |
| 回転の測り方 | 軌跡に**円をフィット**して中心を推定 → 中心まわりの角度を unwrap → 最小二乗回帰で角速度 | ROI 内の密オプティカルフローの**接線成分（渦度）** ω = Σw·(r×v)/\|r\|² / Σw | 軌跡 x(t),y(t) を**窓 FFT** → 主周波数と **位相の直交性 \|sin Δφ\|** |
| 手の重なり | 手ごとに独立トラック。速い方を採用（止まっている手は無視） | そもそも手を区別しない | 点 1 つあれば成立 |
| 一瞬の枠外 | 予測付き unwrap＋トラックを `--coast` 秒生かす | ROI に残った画素で測り続ける | 窓内の欠測を線形補間 |
| 誤検出の弾き方 | 角速度が低い手は自動的に落ちる | **coherence**（接線方向に揃う割合）で並進・カメラ揺れを弾く | **位相直交性**で直線的な往復（機体を揺する）を弾く |
| 反応の速さ | 速い（窓 0.4 秒） | 最速（フレーム間） | 遅い（窓 2 秒。停止だけは `--tail` で速く落とす） |
| RPM の精度 | 高い（合成 60RPM → 60.0） | 概算（同 51〜53。判定には十分） | 中（同 55〜60。分解能 = 1/窓） |
| 弱点 | 俯瞰でMediaPipeが手を取れないと止まる／画面内で速く回る別の手があると拾う | 回っている物が他にもあると混ざる | 起動直後と再始動に 0.5〜1 秒の遅れ／重みが俯瞰向きとは限らない |
| 現地調整 | **不要**（画面のどこで回してもよい） | ROI 合わせが要る | **不要**（同左） |

推し所: B は前提が最も少なく（モデル不要・手の同定不要）**動かすのはいちばん簡単**だが、
下の strict 台本の実測では**誤検出耐性がいちばん低い**（回さずに動かしただけで ON になる）。
A は RPM を数値として使いたい場合、C は周期性だけで押し切りたい場合。
**誤検出を減らすことが目的なら、下の対策版 D を使う。**

## 対策版 3 パターン（D / E / F）

実機で見つかった誤判定に対する対策版。A・B・C はそのまま残してある（比較のため）。

| | D: `rotate_landmark_strict.py` | E: `rotate_periodicity_strict.py` | F: `rotate_pairangle.py` |
|---|---|---|---|
| 元 | A の対策版 | C の対策版 | **旧ロジックの改良版** |
| 直した問題 | 回さずに機体ごと大きな弧に沿って手を動かすと ON になる | 削っていないのに ON が多い | 一瞬の枠外で判定が消える／手が重なると壊れる |
| 追加した判定 | ①正味 1 周以上回ったか ②回転方向の一貫性 ③軌道半径の帯 ④円への当てはまり | ①位相直交を 0.45→0.80 ②x/y の振幅比 ③ピーク卓越度 0.22→0.35 ④主周波数の安定性 ⑤円フィット半径と残差 ⑥正味の回転角 ⑦点の飛び（取り違え）検出 | 基本ロジックは不変。①計算できない間は角度を凍結し直前の角速度を維持 ②予測付き unwrap ③handedness を使わず最近傍でスロット割り当て |
| 代償 | ON までに約 1 周ぶん（60RPM で約 1 秒）かかる | 過渡（手を寄せる・持ち替える）の後、窓 2 秒ぶん判定が出ない | 重なり・欠落が `--hold`＋ゲートのホールド（既定 0.8+0.45 秒）を超えると途切れる |

**D の考え方**: 弧をなぞる動きは半円で折り返すので、**正味の回転角が 360° に届かない**。
「1 周回った」ことを確認してから ON にする（`--min-turn-deg`）。半径帯（`--min-radius` /
`--max-radius`）だけは画角に依存するので、HUD に出る実測半径を見て現地で合わせる。

**E の考え方**: C のしきい値は緩く（`quad>=0.45` は位相差 27〜153° を許す）、ランダムな
揺れが素通りしていた。**円運動としての条件**（位相直交・x/y の振幅比・円フィットの半径と
残差・正味 1 周）と**安定性**（主周波数が跳ばない・点が飛ばない）を足して、
「周期的に見えるだけ」を落とす。

**F の考え方**: 旧ロジック（2 手のなす角の、一定フレーム内の変化）は変えない。
なす角が定義できない瞬間——**片手が枠外／2 手が重なる**——に、値を 0 に落とさず
**角度更新を凍結して直前の角速度を維持**する。加えて、重なりの前後で左右が入れ替わって
角度が 180° 飛ぶのを、最近傍によるスロット割り当てで防ぐ。
（弧をなぞる動きの誤検出は F の対象外。そこまで見るなら D。）

## セットアップ

```sh
cd tools/position-tracker2
uv sync                 # A・B 用（mediapipe / opencv / numpy）。Python 3.12 固定
uv sync --extra yolo    # C も使う場合（ultralytics = torch を含むので重い）
```

`mediapipe` は **0.10.14 固定**。1.x は A が使う legacy の `mp.solutions.hands` を削除しているため。
C の重み（既定 `yolo11n-pose.pt`）は初回実行時に自動ダウンロードされる（ネットワークが要る）。

## 実行

```sh
uv run python rotate_landmark.py            # A
uv run python rotate_flow.py                # B
uv run python rotate_periodicity.py         # C
uv run python rotate_landmark_strict.py     # D（A の誤検出対策版）
uv run python rotate_periodicity_strict.py  # E（C の誤検出対策版）
uv run python rotate_pairangle.py           # F（旧ロジックの改良版）
```

ウィンドウ操作（**B のみ**。A と C は映像全体が対象なので ROI 調整は無い）:

| 操作 | 効果 |
|---|---|
| ドラッグ | ROI（ハンドルを囲む円）の中心を移動 |
| `[` / `]` | ROI 半径 |
| `s` | ROI を `roi.json` に保存（次回起動時に読み直す） |
| `ESC` | 終了 |

共通オプション: `--flip`（左右反転）、`--headless`（ウィンドウ無し）、`--duration SEC`（自動終了）、
`--sim`（カメラ無し）。各パターン固有のしきい値は `--help` を参照。

## 出力（ファイル契約）

1 行 `seq,shaving,rpm`（例 `446,1,59.6`）を ~50ms 間隔で書く。`position-tracker` と同じく
`rotation.txt.tmp` に書き切って `os.replace()` で原子的 rename する（partial read を排除）。

- `seq` … long 単調増加。止まったら「プロセス停止」と判定できる。
- `shaving` … 0/1。`ShavingGate`（ヒステリシス＋ホールド）を通した後の値。**これが判定結果**。
- `rpm` … 参考値（計測不能時は 0.0）。パターンにより精度が違うので判定には使わない。

出力先の解決順: 環境変数 `KAKIGORI_ROTATION_FILE` → `config.json` の `rotationFile` →
スクリプト相対 `out/rotation.txt`。しきい値も `config.json` で上書きできる（`config.example.json` 参照）。

## `--sim`（カメラ無しの比較・自動採点）

合成ソースが 16 秒周期で**旧ロジックが壊れた 2 ケースを含む台本**を再生する。
検出器（MediaPipe / YOLO）は迂回され、**回転判定のロジックだけ**を突き合わせられる
（B は画素ベースなので合成フレームをそのまま処理する）。

台本は 2 つある。`--sim-scenario basic`（既定・16 秒周期）は**旧ロジックが壊れた 2 ケース**、
`--sim-scenario strict`（26 秒周期）はそれに**誤検出を誘発する 3 局面**を足したもの。

| 局面 | 内容 | 期待 | 台本 |
|---|---|---|---|
| `normal` | 両手が見えて等速回転 | ON | 両方 |
| `one-hand` | 片手がフレーム外（0.4 秒） | ON のまま | 両方 |
| `blackout` | **両手とも消える（0.35 秒）** | ON のまま | 両方 |
| `overlap` | **両手が重なる**（0.5 秒かけて寄り、離れる） | ON のまま | 両方 |
| `sweep` | **回さずに機体ごと大きな弧を往復**（半径 192px・1 周しない） | OFF | strict |
| `jitter` | 手は止まっているが検出点が数 px 揺れ、時々左右が入れ替わる | OFF | strict |
| `swing` | 機体ごと直線的に前後させる | OFF | strict |
| `stopped` | 手はあるが回していない | OFF | 両方 |

```sh
uv run python rotate_flow.py --sim                                   # 目で見る
uv run python rotate_flow.py --sim --headless --duration 34          # 採点だけ
uv run python rotate_landmark_strict.py --sim --sim-scenario strict \
    --headless --duration 28                                         # 誤検出込みで採点
```

合成 60RPM・正解が変化した直後 0.8 秒は採点から除外。basic は 34 秒、strict は 28 秒。

**basic（旧ロジックが壊れた 2 ケース）**

| 局面 | A | B | C | D | E | F |
|---|---|---|---|---|---|---|
| normal | 100% | 100% | 95.5% | 95.2% | 63.8% | 100% |
| one-hand | 100% | 100% | 100% | 100% | 100% | 100% |
| blackout | 100% | 100% | 100% | 100% | 100% | 100% |
| overlap | 100% | 100% | 100% | 100% | 33.3% | 100% |
| stopped | 100% | 100% | 100% | 100% | 100% | 100% |

**strict（誤検出を誘発する 3 局面を追加）**

| 局面 | A | B | C | **D** | **E** | **F** |
|---|---|---|---|---|---|---|
| normal | 100% | 100% | 91.5% | **94.3%** | **86.0%** | **100%** |
| one-hand | 100% | 100% | 100% | **100%** | **100%** | **100%** |
| blackout | 100% | 100% | 100% | **100%** | **100%** | **100%** |
| overlap | 100% | 100% | 100% | **100%** | **57.3%** | **48.0%** |
| **sweep**（弧を往復） | 0% | 0% | 0% | **100%** | **100%** | 86.8%※3 |
| **jitter**（検出点の揺れ） | 85.9% | 0% | 17.7% | **100%** | **100%** | **100%** |
| **swing**（直線往復） | 7.7% | 81.6% | 62.3% | **100%** | **100%** | **100%** |
| stopped | 39.6% | 100% | 100% | **100%** | **100%** | **100%** |

読み取れること:

- **A・B・C は 3 つとも `sweep`（回さずに機体ごと大きな弧を往復）を 0% で誤検出する。**
  D はこれを 100% 落とす。B は `jitter` も 0%（＝常時 ON）で、誤検出耐性はいちばん低い。
- **D が総合的にいちばん堅い**。誤検出局面を全て 100% で落としつつ、旧ロジックが壊れた
  3 局面も 100%。欠けは normal の 5.7% だけで、その中身は「回し始めてから 1 周ぶん
  （60RPM で約 1 秒）の ON 遅れ」。
- **E は誤検出を全て落とす代わりに、本物の回転も取りこぼす**（normal 86%・overlap 57%）。
  原因は FFT 窓 1.5 秒で、手を寄せる・持ち替えるといった過渡が入ると窓 1 本ぶん判定が
  出ないため。連続して回す場面では効くが、`holdSec` を上げるか D と併用するのが現実的。
- **F は旧ロジックのまま 2 つの弱点を塞げている**（one-hand / blackout / jitter / swing / stopped
  が 100%）。overlap 48% は「4 秒間ずっと重なったまま」という strict 台本の厳しさによるもので、
  basic の 2 秒の重なりなら 100%。凍結ホールド（`--hold` 0.8 秒）＋ゲートのホールド 0.45 秒＝
  **約 1.25 秒までの重なり・欠落を跨げる**というのがこの方式の限界。
- ※3 F の sweep 86.8% は対策の成果ではなく偶然。合成台本では 2 手の間隔が約 40px しかなく、
  「重なり」と判定されて凍結→ホールド切れで OFF になっているだけ。**F は弧をなぞる誤検出を
  直していない**（それは D の担当）。

この採点は合成データに対するもので、**実機のカメラ映像での精度を保証するものではない**
（検出器そのものは迂回されている）。実機では 3 つを順に起動して HUD で見比べるのが前提。

## 構成

```
common.py                    出力・ROI・ゲート・実行ループ・合成ソース（共通土台）
rotate_landmark.py           A: mediapipe + 幾何（手ごとの角速度）
rotate_flow.py               B: opencv のみ（オプティカルフローの渦度）
rotate_periodicity.py        C: ultralytics + FFT（位相直交判定）
rotate_landmark_strict.py    D: A + 回転の実在検証（周回・方向・半径・真円度）
rotate_periodicity_strict.py E: C + 円運動の厳格判定（直交・振幅比・安定性・周回）
rotate_pairangle.py          F: 旧ロジック（2 手のなす角）＋ 欠落と重なりの凍結ホールド
```

回転の見つけ方は各スクリプトに閉じている。取得・ROI・判定ゲート・書き込み・表示は `common.py`
に集約してあるので、**各パターンの差分は検出ロジックだけ**になっている。
D は A を、E は C をそれぞれ import して継承しているので、差分＝追加した判定だけが読める。

## 接続先（このツールの外）

**Unity へは直接繋がない。** 出力 `out/rotation.txt` を読むのは
`tools/lidar-tracker/valley_tracker.py` で、LiDAR の落氷検知の**隙間を埋める**ために使う。

LiDAR は氷を毎回転は拾えない（実測 0.75〜2 秒に 1 回）ため、従来は 1.5 秒の盲目ホールドで
隙間を埋めており、それがそのまま「削るのを止めてから雪崩が止まるまでの遅延」になっていた。
本ツールが「回っているか」を渡すことで、**回している間だけ**削りを延長できる。

```sh
# カメラ側（このツール）
uv run python rotate_pairangle.py

# LiDAR 側（config.toml の [camera] rotation_file が out/rotation.txt を指していること）
cd ../lidar-tracker && uv run python valley_tracker.py
```

座標は送らない（位置は常に LiDAR のもの）。Unity 側の契約 `seq,x,y,shaving` は不変で、
C# の改修は無い。詳細は `tools/lidar-tracker/README.md` の「カメラ併用で削りの遅延を縮める」。

現在 `valley_tracker.py` が想定しているのは **F（`rotate_pairangle.py`）**。他のパターンも
出力契約は同じなので、実機で見比べて差し替えられる。
